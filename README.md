# 北京食单

北京一人食收藏地图。保留真实菜品照片、店铺位置和出处，支持记录一餐、点赞和评价，可直接部署到腾讯云等 Linux 服务器。

## 功能

- Leaflet 地图、GeoJSON 店铺位置与 Canvas 参考范围；悬停显示首图和店名，点击查看菜品。
- 首屏聚焦北京市区，手机地图约占半屏，桌面保留更宽的地图区域；“北京全览”查看全部参考位置。同坐标的多个分店显示店铺数量，点击展开照片与店名选择，保留原参考坐标。
- 店铺卡片提供高德地图入口，按完整店名（含分店）在北京搜索，确认真实门店后规划路线。桌面使用官方 HTTPS 网页搜索；手机使用 Android／iOS 官方 App 搜索 scheme，Android Chrome 的 Intent 带网页版 fallback。iOS 和其他浏览器提供独立网页版入口，不用计时器猜测是否安装 App。参考位置不会作为导航终点发送。
- “我的位置”区分等待授权、正在获取和获取较慢；在当前页面复用 2 分钟内的位置并后台刷新。用户等待时拖动／缩放地图，结果只更新蓝点，不把视野跳回。定位后按当前位置、手动浏览后按地图中心的参考距离排列，距离为粗略直线距离。坐标仅在页面内存使用，不写业务数据库或日志，底图仍由浏览器向现有瓦片服务请求。
- 投稿仅需自由填写完整店名（含分店）、地址、菜品和 1–3 张菜品图；体验、人均、日期和来源链接选填。地图选点可选，不要求已有店铺。
- “导出地点”一键读取最新公开食单并下载 UTF-8 Markdown，包含地址、菜品、WGS84 参考坐标、菜品图片链接、可选人均／体验／日期和公开来源，可交给其他 AI 规划。导出不包含账号、审核记录、草稿或来源 token；图片作为链接提供，不打包图片。`FOOD_EXPORT.buildGeoJSON` 另提供标准结构化输出供集成。
- 每个账号可点赞／取消，同一店铺的不同用餐记录各自保留反馈；评价可自述实际到店体验。同品牌分店在卡片中互相跳转，铃木北新桥、杨梅竹斜街、帽儿胡同、丽都四店统一品牌；帽儿和丽都是分店地点资料，菜品与营业状态待确认；高德可检索北京其他分店，当前清单不声称包含品牌全部在营门店。
- 等位反馈按独立分店共享，记录北京时间、人数、店员预计／至少已等待／实际等位及备注。未反馈时为未知，不视为不用排队；超过 2 小时转为历史反馈，不预测实时等待。浏览无需登录，提交和本人撤回需登录；最近 30 天的观察可录入，每账号 10 分钟最多 10 条，撤回保留审计与限流计数。
- SQLite 持久化账号、投稿、点赞、评价和图片元数据，受控文件目录保存图片。部署升级不会覆盖数据。
- 未提交图片仅上传者可预览；成功关联食单后才能公开读取，GET/HEAD 使用同一边界。反馈和上传图片仍禁止共享缓存。
- 自主账号登录、邀请注册、服务器会话、CSRF 校验和登录限流。腾讯云实例开放浏览，记录新食单、上传和评价等写入需登录。

## 本地运行

需要 Node.js 22.18 或更高版本，以及 pnpm。

```sh
pnpm install --frozen-lockfile
cp .env.example .env
pnpm build
pnpm start
```

默认地址是 `http://127.0.0.1:8790/`。初次运行按 Drizzle 迁移创建数据库；已应用迁移按哈希校验，不允许改写历史迁移。

首次账号通过 `pnpm user:create` 从标准输入读取 JSON：`username`、`password`、`displayName`。用户名 3–32 位小写英文／数字／下划线／短横线，密码至少 12 字符。避免把密码放在 shell 参数或 Git 中。设置私密 `REGISTRATION_CODE` 后，可以在登录页面邀请注册；留空则关闭自助注册。

测试：`pnpm test`。测试使用独立临时目录，覆盖真实持久化、点赞与投稿去重、图片所有权、认证、CSRF、事务回滚、迁移完整性和路径限制。

## 数据维护与验证

初始收藏由 `public/shops.js`、`public/photos.js` 和 `public/photos/` 维护；构建生成初始数据库数据。新增用餐记录、点赞、评价和上传照片不写回 Git，保存在服务器独立数据目录。分店按店名与地址去空白后的组合识别，同址同名复用分店，每餐保留独立记录；别名和错字不自动归并。

浏览器将照片压缩为最长边 1600px 的 JPEG；服务器对 JPEG／PNG 做真实解码校验（单张不超过 5MB、2000 万像素），图片字节写入 UUID 文件，数据库记录其归属和食单关联。未关联图片仅上传者可读取，关联公开食单后才允许公开 GET／HEAD。图片和数据库都与代码发布目录分开，服务重启或部署不覆盖。

`tests/upload-lifecycle.test.mjs` 使用真实 HTTP、隔离数据库和有效 JPEG，覆盖新店名、图片关联、所有权、幂等、分店归并及服务重启；不会在生产写测试食单。客户端 WebP 转 JPEG 的表单链路另在本地浏览器实际检查。

每日备份由 `deploy/beijing-food-map-backup.timer` 在服务器本地时间 04:30 触发，脚本使用 SQLite 在线快照并复制 media 到 `/var/backups/beijing-food-map/`；升级前也执行备份。当前备份在同一台服务器，未配置异地副本和自动滚动保留。未关联照片可由上传者删除，尚无定时孤儿回收。已发布食单尚无自助修改／删除入口，首次补齐缺失的分店坐标会同步到该店各食单，已有坐标不被新投稿覆盖；坐标来源保留为参考资料或用户手选，服务重启不会重置补录位置。

高德入口参考：[网页搜索](https://lbs.amap.com/api/uri-api/guide/search/search)、[Android App 搜索](https://lbs.amap.com/api/amap-mobile/guide/android/search)、[iOS App 搜索](https://lbs.amap.com/api/amap-mobile/guide/ios/search)、[Chrome Intent 回退](https://developer.chrome.com/docs/android/intents)。手机传入“北京 + 完整店名”的搜索条件；没有 POI ID 时由用户确认候选门店，当前参考坐标不作为精准导航终点。

## 腾讯云部署

推荐结构：

- `/opt/beijing-food-map/releases/<commit>/`：代码版本。
- `/opt/beijing-food-map/current`：当前版本软链接。
- `/var/lib/beijing-food-map/`：数据库及图片，归独立 `foodmap` 用户所有。
- `/etc/beijing-food-map.env`：服务器配置，权限 `0600`，仅管理员读取。

1. 构建并上传源码和 `dist`，安装锁定的生产依赖。
2. 将 `.env.example` 的配置写入服务器专用配置文件；`APP_ORIGIN` 为真实 HTTPS 域名或已配置证书的 IP，`BASE_PATH=/food/`，`PUBLIC_READ=true` 开放查看；改为 false 可恢复私有浏览。
3. 使用 `deploy/beijing-food-map.service` 启动独立 systemd 服务，Node 只监听 `127.0.0.1:8790`。
4. 将 `deploy/nginx-food-limits.conf` 安装到 Nginx 的 HTTP 上下文（例如 `/etc/nginx/conf.d/`），将 `deploy/nginx-food.conf` 包含在现有 HTTPS server 中；运行 `nginx -t` 成功后 reload。动态 API 按 IP 5 次/秒、突发20限流，超量返回429；静态照片不共用该额度。模板保留 `/food/` 前缀给 Node 处理，不占用现有根路径。
5. 使用 `deploy/backup.mjs` 备份数据库与图片，升级前先备份；数据库迁移保持追加。跨版本回滚代码时必须保留数据库已应用的迁移文件，不能直接用少了追加迁移的旧发布目录启动；数据库与图片恢复须使用同一次完整备份。

## 源码与数据边界

`public/` 包含 65 家原帖收藏、2 家补充的铃木分店地点资料、76 张网页照片和必要出处；源链接去除了短期验证参数。原始研究记录、OCR、未确认帖子、平台配置、会话、上传数据、缓存和凭据不在公共仓库中。

店铺和照片整理于 2026-10-04。店铺信息会变化，地图上的参考位置不等同于实时导航。照片来自其对应原帖，原作者保留照片权利；图库与代码的使用权需分别处理。

`worker/index.js` 保留食单业务逻辑，通过小型 SQLite／文件存储适配器运行于 Node。身份由本站会话验证后传入，不依赖或信任浏览器提供的平台身份标头。原 Sites 部署与此服务器版本相互独立，原数据库中的正式用户数据需要单独迁移。
